# nestjs框架基础

## 框架思想
1. OOP（面向对象） 关注的是纵向的层级关系（继承、多态），解决的是业务实体的建模。
2. AOP（面向切面） 关注的是横向的通用逻辑，解决的是系统级服务的复用和解耦。

## 框架技术
1. IOC（控制反转） 是设计思想，是一个容器，从“你自己创建依赖”反转为“外部容器为你创建并管理依赖”
2. DI（依赖注入） 是实现这种思想最主流的具体技术。将组件所需的依赖，通过外部方式“注入”到组件内部，而不是由组件自己创建依赖。
3. reflect-metadata 是实现 DI 和 IoC 的关键技术基石，它解决了在 JavaScript/TypeScript 中“如何知道一个类需要什么依赖”的核心难题。
::: tip
  + reflect-metadata 是 TypeScript 提供的一个标准库，用于在运行时为类、方法、属性等添加和读取额外的元数据
  + 编译器自动将构造函数的参数类型以元数据的形式保存了下来.`__metadata("design:paramtypes", [依赖的类、方法、属性])`
  + 使用 `Reflect.getMetadata('design:paramtypes', 使用依赖的类)` 方法，读取使这个类的元数据
  + 获取到依赖类型列表后，IoC 容器就可以递归地为每个依赖创建实例
:::

## @Module装饰器描述模块

### @Module属性
1. imports：导入其他模块，实现模块之间的依赖关系。
  + 数组定义了当前模块所依赖的其他模块。这是模块之间建立联系的桥梁。
  + 导入其他模块，使得被导入模块通过 exports 暴露出来的 providers 可以在当前模块中被使用。

2. controllers：定义模块的控制器，处理 HTTP 请求。
  + 当前模块的控制器清单。控制器是应用接收 HTTP 请求的入口点，负责处理路由、解析请求参数并返回响应。
  + 定义路由，接收外部请求，并调用 providers 中的服务来处理业务。

3. providers：定义模块的服务，实现业务逻辑。
  + providers 数组定义了当前模块的服务清单。这些是 NestJS 的 IoC 容器负责实例化和管理的类，通常包含业务逻辑、数据库操作等。
  + 将服务注册到当前模块的依赖注入容器中。
  + 告诉 NestJS 的 IoC 容器：“在当前这个模块里，我需要使用这些服务，请为它们创建实例并管理起来。”
  + 只有在 providers 数组中列出的服务，NestJS 才会为它创建实例（默认是单例）。

4. exports：导出模块的服务，使其他模块可以使用。
  + 数组定义了当前模块的公共API。它将当前模块的一部分 providers 暴露出去，供其他通过 imports 导入本模块的模块使用。
  + 将本模块的 providers 共享给外部模块。
  + 必须是当前模块 providers 数组中已定义的 providers。
  + 注册后，当前模块的 Controller 或其他 Provider 才可以通过构造函数注入来使用它。

## @Injectable
1. 标记一个类，使其可以被 NestJS 的 IoC（控制反转）容器管理。
2. 允许被注入：没有 @Injectable() 的类，无法在构造函数中被注入。
3. 支持依赖注入：如果一个类（如 UserService）的构造函数中需要注入另一个类（如 DatabaseService），那么 UserService 本身必须加上 @Injectable() 装饰器。这是为了让 NestJS 能够读取并注入它自己的依赖。
4. 让一个类有注入的资格(作为消费者类)和被注入(作为依赖)的资格。让别人能用你的服务，让你能用别人的服务。

## DTO （数据传输对象）
1. 接受部分数据
2. 验证数据
3. 不对应数据库表
4. 属性小于或等于数据库表的字段
## DAO （数据访问对象）
1. 封装数据库操作
2. 与数据库表对应
3. 与业务逻辑分离
4. 与数据库表结构保持一致
